# Decisions made while building (not in the design doc)

Each entry: what, why, and how to undo it. Newest last. The design doc (`DESIGN.md`) stays as written; where reality disagreed, this file records the deviation.

## D36. Amounts are numbers of cents and may be fractional (legacy fidelity)
**What.** `*_cents` columns hold cents as JS numbers. Anything that comes from a bank, an alert, a CSV or the UI is a whole number of cents; the legacy import preserves the sheet's amounts exactly, so a few values are fractional cents.
**Why.** The real `Transactions` sheet has 3,000+ rows with half-cent or finer amounts (`-13.765`, up to 6 decimals from `SplitCost`), and budget targets like `=400/12` and History values like `16.66666667`. Rounding each to whole cents would drift lifetime balances by dollars (hundreds of half-cent rows in one category). The design's "integer cents" goal was written without seeing this data.
**Consequences.** Parity compares within half a cent (`TOLERANCE_CENTS` in `src/migration/parity.ts`), because the sheet itself adds a float transaction sum to an accrual rounded by `toFixed(2)`. Negative zero is avoided (`0 - x`). The UI formats to cents. New data stays integer, so drift can only come from the legacy rows.
**Undo.** Round legacy amounts on import (one line in `src/migration/sheet.ts`) and accept the drift.

## D37. Real parity result
`npm run hk -- migrate` on the real BudgetProgram export: 619 checks, 0 mismatches (P1 months and totals, P2 lifetime transaction sums, P3 `Current`, P4 spent/gained for the last two months with data, P5 count and total, P6 allocated). Notes on how the oracle is read:
- The sheet counts **months only up to a retired category's last stop month** (exclusive); live categories count through the current month inclusive. Parity encodes exactly that.
- Blank-category rows are their own group in `Internal!A:B` (`(blank)`), separate from `NEEDS CATEGORY`.
- The cached "this/last month" blocks were empty (no transactions since July 2026), so P4 uses an independent re-implementation of the sheet's QUERY for the last two months that have data (`tools/xlsx_to_export.py`).
- `Internal` formulas in the xlsx show `Transactions!C2:D1501` but the live sheet uses open-ended ranges (`temp` tab); the cached values match the open-ended version (checked against the sum of all 17,595 rows).

## D38. Greenlight: shapes the design did not list
Seen in the real corpus (154 messages): `X withdrew $N from|at VENDOR`, three declined variants (spend control, insufficient funds on card, exceeded PIN attempts, bare "was declined"), `X entered an incorrect PIN` (noise), plus a request shape from `IFTTT_Code.gs` (`X requests $N to ...`). All parse; every captured message parses to a known shape.
**Withdraw policy.** Default `ask`: an ignored transaction is created and **flagged** so it appears in the inbox. `ignore` drops it; `debit_category` books an extra allowance debit. Under option A the allowance already charged the profile, so a withdrawal never re-charges on its own.
**Requests.** A request message creates a *pending* request and notifies; it never posts a charge (§11.5). The approval message is still unseen (D23).

## D39. Chase alert shape comes from the old script
`Prime Visa: You made a $X transaction with VENDOR on <date> at <time> ET.` The parser searches for the sentence (so an email body wrapping it works), parses Eastern wall-clock time with a real tz database **at the alert's own date**, and stores `occurred_on` as the Pacific date. Creates a *provisional* transaction; the CSV row later supersedes it (tolerance matching for tips).

## D40. Suggestion ranking has a fallback
`suggestionsFor` ranks: the suggesting rule, the merchant's past categories, similar descriptors, then your most-used expense categories (last ~120 days). Without the last step a brand-new merchant produced a prompt with no one-tap answers.

## D41. Merchant bootstrap never sets default categories
History books restaurants to personal buckets (`Brys Spending`, `Miracle Spending`, `Miracle Cash Overflow`), so a majority-category default would suggest those for every DoorDash order. The backtest of your real `IFTTT_Guess.gs` rules against all history confirms it: the largest "disagreements" are person buckets, not rule errors. Merchants are created `unreviewed`; you decide defaults on the review page.

## D42. Backtests are read-only
`suggestCategory(..., { readOnly, rules, aliases })` does not create merchants or bump rule hit counts, and caches rules (35 s -> 2.8 s over 16,675 rows).

## D43. Indexes
`transaction_splits(transaction_id)` was missing; the close checklist took 5.5 s on the real data. Added with four other indexes; a perf guard test (`test/perf.test.ts`, 20k rows) fails if it regresses.

## D44. Experimental receipt parsers are opt-in
(Superseded by D66: the parsers are now real and on by default.) `HK_EXPERIMENTAL_PARSERS=1` registered Amazon/Venmo/PayPal email parsers written from the *common* shapes (no real samples yet). They are strict-or-unrecognized, only write `external_notes`, and are off by default so a wrong guess can never create data. Replace the regexes with real fixtures after the discovery month.

## D45. Test strategy
Vitest stays (unit, property/fuzz, API via `fastify.inject`, parity). Browser e2e is **Web Test Runner + headless Chromium** (`npm run test:e2e`): it boots the real Fastify API with the demo database and drives the real Lit UI. CI (`.github/workflows/ci.yml`) runs typecheck, unit, build and e2e. Tests that need your private export skip themselves when it is absent; their setup lives in `beforeAll` because a skipped `describe` body still runs.

## D46. The e2e suite found real UI bugs
Split editor lost edits on re-render; buttons stayed disabled after typing because forms mutated nested objects (Lit does not re-render). Fixed; the tests that found them stay.

## D47. Sign-in is testable without a Google client ID
`/auth/me` reports mode and user; `registerAuth` takes a `verifyIdToken` function (default: Google's tokeninfo endpoint). Tests inject a fake verifier. Real sign-in only needs `HK_GOOGLE_CLIENT_ID` and `HK_ALLOWED_EMAILS`.

## D48. Notifications
Real-time pushes only for the fast lane (Chase alerts, Greenlight); CSV-derived items wait for the morning digest. Unknown purchaser -> both phones; the first answer sends a `close` push to the other. Replay of stored events is silenced. Push transport is pluggable (`memoryTransport` in tests; nothing leaves the process). VAPID keys are generated once into `settings`.

## D49. Auth is enforced by matched route, not raw URL
A request to `/%61pi/...` bypassed a prefix check on the raw URL. Protection now keys off `req.routeOptions.url`, so whatever Fastify routes to `/api/*` is protected. Logout requires the CSRF header.

## D50. Review fixes to money paths
- Go-live deletes later budget versions of the changed categories (audited) so an old future version cannot silently override the plan; plan items for non-active categories are ignored.
- Sub-cent legacy drift (< 0.5 cent) is not an overage or a nonzero pool; rebalance donor capacity is floored to whole cents.
- Retire uses the real month end (the 28th dropped 29-31 spend).
- Pairing needs transfer-like descriptors on both legs; the notes matcher treats `needs_note` rows as terminal; notes CSV dedupe is multiset-based.
- Greenlight final-amount: containment beats a shared token, closest amount then date wins, a token-only match is refused when ambiguous; a user-split reclass is flagged, never collapsed. Unrecognized/noise outcomes are not recorded as processed so replay can reprocess them after a parser fix.
- Item splits with unknown order total: subset search tolerates up to ~15% tax/shipping (5% under, for promos).

## D51. Reconcile semantics
Provisional rows match posted rows exact-first, then by unique tolerance; stale provisionals still match; superseding carries kind, pairing, owner, note state and repoints matched notes; de-dup is scoped to the account; import profile signatures are institution-prefixed.

## D52. Late Chase alerts
An alert whose charge already posted via CSV (same account, amount, date within 2 days, shared descriptor token) attaches to the posted row (`late_alert`) instead of creating a duplicate provisional.

## D53. Deployment is scripts, not instructions
`make bootstrap` is idempotent and is also the update path (deploy tasks live in the top-level Makefile; only `Caddyfile`, the systemd unit and the env example remain in `deploy/`); it keeps its settings in `/etc/hearthkeeper.env`. Code reaches the VM as a `git archive` tarball over ssh, so the VM needs no git credentials. Data moves as a verified snapshot (`hk snapshot` / `hk verify`: checksums, row counts, SQLite integrity, money invariants, schema-version check) rather than by re-running the migration on the server, so the server never needs the spreadsheets. Rebuilding from the sheets stays a laptop-side, repeatable script (`build-prod-db.sh`).

## D54. No app-level backups
Backups are GCP disk snapshots (daily schedule, `gcp-setup.sh` prints the commands). The nightly job, bucket and its permissions were removed. Only the on-disk rollback copies taken before an update or a data install remain.

## D55. "Needs category" is an envelope you can see
Uncategorized transactions were already outside every envelope (they sit in the `needs_category` state), which made the sheet's NEEDS CATEGORY category look like it had zeroed out: its legacy rows net to $0.20 because reingest credits offset them. Rather than force a number, the Budget page, Home and Dashboard now show a "Needs category" total (sum of every transaction still waiting for a category, with count). Categorizing a transaction moves its amount out of it and into the chosen category, and the confirm dialog shows that category's balance before and after. The starting figure is whatever is uncategorized after the bank backlog is imported. Parity is untouched (display only).

## D56. Information architecture and UI rules
Top level: Home, Budget, Backlog, Transactions. Data: Categories, Transfers, Plans, Earnings, Imports, Close. Discover: Dashboard, Analytics, Explore. Settings: Preferences, Greenlight, Rules & merchants, Ingest health, Migration. Every page opens with an explanation block; table headers carry hover help; spacing comes from one token scale (`--gap`, `--page-x`) so every page shares margins. Lists are rows or cards, never chips. Every category dropdown is the type-to-search `hk-category-select`. Dialogs are native modal `<dialog>`s so they always sit above the page. Theme (match device / light / dark) is a per-device setting in Preferences.

## D57. Every Home/Backlog item says why it is there, and counts are true counts
The inbox returns real totals (not the 200-row list limit) and a plain-language reason per item (no rule matches, left in NEEDS CATEGORY, your "???" note, waiting on a note, pending too long). Home's headline is the true number of distinct items; the Backlog groups uncategorized items by merchant, so its list is shorter than the count by design, and both pages say so. Greenlight reclasses are shown and booked at their real spend, not their zero total.

## D58. Everything from the spreadsheet import is valid as it stands
Nothing that predates the seed is asked for a category or a note. `grandfatherSeed` (run after parity in `hk migrate`, by `hk grandfather`, and at every server start; idempotent and instant once done) moves the imported rows that had no category to a reserved category, "Predates Oct 2026 Seed" (`categories.system = 1`, kind `income_reference`, retired). It cannot be picked, used in a rule, unretired or shown on the Categories page, but the name appears on the transactions that carry it. Imported Amazon/Venmo/PayPal rows with no note get the note "Predates Oct 2026 Seed". Every imported row is marked (`note_source = 'seed'`) so the note matcher never flags it later. New transactions after the seed still need categories and notes. Bare "???" follow-up flags from the sheet are cleared with the same note (the one flag with a real remark, "FLAG: needs follow-up ...", stays). Only rows written by the initial sheet import are touched (their splits carry origin `legacy`, which nothing else writes); bank CSV imports and live capture are never affected.

## D59. Pop-ups
Dialogs that ask for a decision (confirm, categorize, retire, add) ignore outside clicks; Esc still cancels. Informational dialogs and the transaction detail close on an outside click. The category list renders inside the dialog it opens from, because only top-layer content can sit above a modal. Hover hints are click-through, so they vanish when the pointer leaves the item. Opening one nav menu closes the others.

## D60. Answering a Greenlight spend re-attributes it
A Greenlight spend has a zero total (the allowance already charged the child's category). One-tap answers from Home, Backlog or the API used to replace its two offsetting splits with a single $0 split, so nothing moved. `answerCategory` now writes the offsetting pair (chosen category -spend, the child's category +spend). Failed saves on Home/Backlog show a dialog with the server's message; the category picker no longer lets the inner input's native `change` event escape as a malformed one.

## D61. One card per transaction, one way out per open reason
A transaction can wait on several things at once (a category, a note, a flag, a pending charge that never posted). Home and Backlog now show it once, list every open reason, and give each its own action: category options, note (pick a matching note, type one, or "no note needed"), "Mark as reviewed", "Hide it: it never posted". Categorizing one reason leaves the card in place showing "✓ Category: X" and what is still open; saves are confirmed with a toast. Before this, an uncategorized Amazon/Venmo/PayPal payment looked unchanged after you categorized it, because it was still waiting on its note.

## D62. Checklist cards
Home and Backlog cards show Category and Note (and Flag / Never-posted when they apply) as a checklist: a large "?" for what is missing or unknown, a check when settled, and a dash for a note that is not needed. The best category guess is one button ("Use Groceries"); other suggestions and the full search are collapsed; the account, the bank's full line, nearby transactions and "Not a budget item" sit behind Details. A note can be added or edited from any card. The Transactions list shows notes in place of the account (the account is in the row's detail).

## D63. Home order
Needs attention first (collapsible, open by default, the choice remembered per device), Favorites second, Recent third; searching and Add transaction come last. No intro text on Home. On phones, favorites are 2-column tiles of three short lines (name, balance, spent of target) with the pace bar as a strip along the tile's bottom edge, and the star (pinning) moves to the Budget page, taking each tile from ~87px to ~72px tall.

## D64. Needs attention starts collapsed; one phone automation can feed Chase too
The Home "Needs attention" section is collapsed on a fresh device (the count stays visible in its heading) and remembers how you leave it. On the device channel a Chase card alert sent without an explicit `source` is recognised by its wording and stored as `chase_alert`, so a single IFTTT automation can forward both Greenlight and Chase notifications. Setup steps are in `docs/CAPTURE.md`.

## D65. Notification devices: one switch per device, no master checkbox
Settings lists the signed-in person's devices (browser and OS from the user-agent, "This device" badge, added and last-delivered dates) with Remove, and the main button reflects this browser: "Turn on notifications on this device" when it is not subscribed, "Turn off notifications on this device" when it is. The old "Send push notifications to me" checkbox is gone from the UI because it duplicated what removing devices does and nobody could tell the two apart; the stored preference remains, and if an old setting left it off a banner offers to turn it back on. The unsubscribe endpoint now only removes the caller's own subscriptions. `sudo make tokens` prints the ingest token secrets from the deployed app.

## D66. Receipt and Wells Fargo parsers are real and on by default
Parsers for Amazon "Ordered N items", Venmo paid/received, PayPal receipt and merchant payment, and the Wells Fargo "account update" alert were rewritten against real emails (sanitized fixtures in `test/fixtures/receipts`). The forwarder's HTML part is rendered to lines by the server (`src/receipts/text.ts`) because Venmo's plain part is empty and its amounts are split across elements. Still strict-or-unrecognized; receipts only create notes; `HK_DISABLE_RECEIPT_PARSERS=1` is the off switch. A Wells Fargo alert creates a provisional transaction on the account with the matching `accounts.last4` (editable in Settings; no match is an error that replays once set), skips lines already present, and is superseded by the bank CSV like a Chase alert, so CSV uploads that overlap emailed transactions are safe. Amazon's email names no products, only categories per order, so notes are category-level. Unverified: Wells Fargo deposit lines and multi-line alerts (assumed to share the withdrawal layout).

## D67. The email's HTML part is stored (raw_events.html) and is what the receipt parsers read
The ingest endpoint used to keep only the plain-text part, so Venmo (empty plain part, amounts split across elements) and PayPal (plain text loses the layout) could not parse in production even though tests, which fed HTML directly, passed. Migration 7 adds `raw_events.html`; the ingest endpoint stores it (capped at 400 KB); parsers render it with `htmlToText`. A resend of an event stored without HTML fills it in and re-parses it. The tests for these parsers now go through the real signed ingest endpoint.

## D68. Hand-forwards are recognised by the server; Chase's alert email has its own shape
The trust decision for a household member's hand-forwarded mail moved from the receiver script to the server (`src/ingest/forwarded.ts`, applied in `parseEvent`): known user address + authenticated forward + quoted sender on the trusted list. It therefore works on events already stored, via Replay. Chase's own alert email (subject "You made a $N transaction with MERCHANT", body "Date Oct 6, 2026", no time of day) is parsed to a provisional transaction with the date only (`authorized_at` null), alongside the existing sentence-with-time shape. Only one real Chase email was seen, and only its first part: the rest of the body (merchant and amount rows) is unverified.

## D69. Merchants are a to-do list of shops without a usual category; ingest messages are a real paged list; "can't tell" is not "signed in"
Merchants are created automatically from the cleaned bank descriptors (thousands from the import), so "new/unreviewed" was noise, not work. The page now defaults to merchants you have actually bought from that have no usual category, most-used first; setting one saves in place with a confirmation of what will happen (suggest / auto / ask are editable per merchant), and Rename and Merge sit behind one "Fix name…" button that explains both. Rows are keyed by merchant id so a picker can never show the previous row's choice. Ingest health gained a Messages tab: every raw event ever received (they are all kept so parsers can be fixed and replayed), newest first, server-paged and filterable, one line each, expandable to the full message with Replay and Mark-as-noise. When `/auth/me` cannot be reached the app now shows a banner saying it cannot tell whether you are signed in, shows saved data read-only, and keeps retrying (on reconnect, on tab focus and every 20s), instead of silently behaving as signed in. Budget shows allocated / income (unallocated) as one card.

## D70. Months replaces the month-end close: a checklist per month, no lock
The close checklist, the period soft-lock and reopen were removed (D-series entries on closing are superseded). The Months page lists every month from the first transaction to today, newest first. Each month shows what is left to do (data from every account, categorized, notes, flags, never-posted pending charges, duplicates, unpaired transfers, Greenlight) with a count and a link to the exact transactions or page that fix it, plus quick numbers (income, spent, net, planned, transaction count, envelopes spent over plan, biggest category). A month is simply done when its list is empty, so a late bank file can make an old month need attention again, which is the point: nothing is locked and nothing needs reopening. The definitions of "needs a category / note / flag / pending" are one shared SQL (`INBOX_WHERE`) used by Home, Backlog, Months and the Transactions filter, so counts and links agree. Coverage rule: an account silent for under 90 days is expected to have data through each month's end (so a stopped upload shows up in every month since); one silent longer is treated as closed; and when the whole household has no transactions after some date, every month since says so (this is how history imported under the Legacy account, with live accounts not yet uploaded, appears). Also fixed: "Hide it" on a never-posted pending charge now actually clears it from Needs attention, and a charge hidden that way counts again if the bank later posts it.

## D71. Needs-you items are two-line table rows in the Transactions column order
Home's Needs attention and Backlog replaced the checklist cards with one shared row (`txnRow`): Date, Description, Amount, Category, Note, the same order as the Transactions table (which was reordered to match; the account stays in the details). A missing category is a dropdown in the Category cell with the best guess one tap away; a missing note is an input with icon buttons for the matcher and "no note needed". The thin second line carries the Details toggle and any other open reason (flag with "Mark reviewed", never-posted with "Hide it"); Details holds why it needs you, the account, the bank's raw line, change-category and edit-note inputs, Nearby and "Not a budget item". On a phone the cells stack (description and amount, date, category, note). In Backlog, merchants with several transactions keep a bulk bar above their rows; one-off merchants share a single list.

## D72. Backlog is server-paged; saves block input; imports flag wrapper charges for notes immediately
After a big import the Backlog was slow because every load and every answer fetched the whole inbox (suggestions computed per row, 2-3 s on 16k+ transactions) and rendered hundreds of rows. Now `GET /api/backlog` returns one page (merchant groups with their rows, or a page of flagged / waiting-on-note transactions) and only that page pays for open reasons and suggestions (about 100 ms); the "frequently used" suggestion lookup is shared across a request; Home asks for just 10 items (`/api/inbox?limit=10`). Categorizing itself was never slow (500 transactions with a new rule: about 120 ms); the cost was the full reload afterwards, which is now a single page refresh. Every save from a row or a merchant group runs behind `withBusy`, a modal that blocks all input (Esc ignored) until the save and the refreshed page are in, and appears only if it takes longer than a moment. Backlog also shows a loading card while the first page arrives. The note matcher now runs at the end of every bank CSV import (and once at server start), so Amazon / Venmo / PayPal charges are on Waiting on notes straight away instead of after the next 10-minute timer; the import result reports how many are waiting and how many notes matched.

## D73. Rule priority is editable; any transaction can be split from its row
Priority was already how the engine ranks rules (lowest number wins, then the rule with more conditions, a tie with different categories is left to the person) but the page only displayed it. Each rule's priority is now an editable number (1 to 9999, validated on the server) and the new-rule form has a Priority box; the list re-sorts itself. Backlog and Home rows have **Split…** in Details: a dialog of parts (category and positive amount each, "Add a part", "Split evenly") whose Save stays disabled until every part has a category and an amount and the parts add up exactly; the original sign is applied on save and it uses the same endpoint as the Transactions page. Greenlight spends (zero-total reclasses) cannot be split from here.

## D74. Merchants only suggest; rules are always the household's own and are made while categorizing
Before, "learn this" silently created a `learned` rule per merchant, a merchant could hold an `auto` default, and rules were promoted after enough clean confirmations. That mixed automatic guesses with decisions the household made, so rules were hard to steward. Now: (1) a merchant has no stored rule. Its suggestion is the category the household chose for it most often (`merchantHistory`: user answers and imported sheet history only, never what a rule did), derived from the transactions so an exception moves the count by one and nothing can go stale. (2) A merchant never rises above a suggestion. (3) Rules (origin `user` or `legacy_guesser`) are checked first; when a rule and the merchant disagree both answers are offered, labelled. (4) A rule is created only when the person ticks "Make a rule" in the categorize dialog (or "Make a rule…" on a merchant), with a live backtest; there is no "remember" box and no auto-promotion, so the ✓/✗ counters are no longer shown. The Rules page no longer has a "New rule" form (use the dialog). (5) A rule's match is a list of clauses that must all hold (AND); a clause is one condition or `any_of` alternatives (OR). Migration 8: merchants set to `auto` become ordinary auto rules, `learned` auto rules become `user` rules, learned suggest rules are removed. Backlog merchant cards are pinned (`keys=`) while answering so a card never moves when its count changes. Not done: creating a rule does not re-classify transactions already waiting in the Backlog.

## D75. Flagging: any transaction, at categorize time too; flagged first on Transactions
`transactions.flagged` already fed Needs attention. Now the Transactions page has a flag button per row (optional reason) and in the detail dialog, and `GET /api/transactions` orders `flagged DESC` before date, so flagged rows sit at the top (across pages) until unflagged. The categorize dialog (Home, Backlog single rows and merchant groups) has "Flag for review" with an optional reason, sent as `flag` to `/categorize` and `/inbox/bulk`. A flagged, categorized transaction therefore also stays in Needs attention / Backlog "Flagged" until marked reviewed. New rules: the Rules tab again has "New rule" (same dialog as "Make a rule…"); conditions include `amount_abs` (is exactly / at least / at most / between, on the size of the amount) and `direction`.

## D76. Note matching compares the size of the amount
The Amazon/Venmo/PayPal skills export `Date,Amount,Note` with the amount of the charge unsigned (`40.85`), while the bank row is negative (`-4085`). The matcher required equal signed amounts, so no note ever matched. It now compares absolute amounts (a same-sign note is preferred when two compete). An Amazon row whose note starts with `UNKNOWN` (the skill could not find the order) is matched but not used as a note: the transaction goes to "needs a note" with the reason shown. Already-imported notes match on the next matcher run (server start, import, or the 10-minute timer); no re-upload is needed.

## D77. Wells Fargo checking CSVs: merchant cleaning for ACH lines, and an account per file
Real exports (`DATE, DESCRIPTION, AMOUNT, CHECK #, STATUS`) parsed fine for date and amount, but (1) `MONEY TRANSFER AUTHORIZED ON 09/09 CASH APP*JAMEEL WI …` was cut to "MONEY TRANSFER AUTHORIZED" (the P2P rule removed everything after "ON mm/dd"), and ACH lines (`COMPANY  TYPE  YYMMDD|MMDDYY  ID  NAME`, payroll, bill pay, student loan, State Farm…) kept their date codes, ids and the holder's name, so every payment became its own merchant. `cleanDescriptor` now treats MONEY TRANSFER like PURCHASE, cuts ACH lines at the first date code / long id / long mixed reference ("ROCKET MORTGAGE LOAN", "GREENLIGHT APP", "SEQUOIA ONE PEO, PAYROLL"), strips "REF NUMBER" and the in-branch cash line, and maps `ORC*xxxx REGION` to ORCA. (2) The Imports page never asked which account a file belongs to, so all three accounts' files were filed under the first Wells Fargo account. Each bank file now needs an account (chosen automatically when the bank has one), and re-importing a file with an account named *adopts* rows that an earlier import filed under the institution-wide fingerprint: they are moved to that account and re-fingerprinted rather than duplicated (`adoptMisfiled`). `recleanDescriptors` (once per DESCRIPTOR_VERSION, at server start) recomputes stored names, moves changed rows to the right merchant, re-runs rules on rows still waiting, never touches your categories/notes/splits, and removes empty unreviewed merchants.

## D78. Importer: quoted headers no longer break the mapping; saved mappings are visible and deletable
The mapping wizard built its column choices by splitting the first line on commas, so for `"DATE","DESCRIPTION",…` it saved the names with their quote marks (`"DATE"`), which never matched the parsed header: every row failed with "missing date". The preview now returns the parsed `columns`, the wizard uses them, and column names are compared without case, spaces or stray quotes, so a mapping saved the old way works too. The Imports page lists every saved mapping in words (`GET /api/imports/profiles`) with a Delete (`DELETE /api/imports/profiles/:id`, audited); deleting never touches transactions, the layout just asks for its columns again.

## D79. Greenlight is a payment with a note, not a subsystem (supersedes the wallet/allowance/reclass design, §11)
Hard to follow in practice: funding was hidden as an internal transfer, allowances charged a child's category, spends were reclassified with zero-sum splits, and requests/forecasts/a wallet balance lived on their own page. Now: (1) a bank row `GREENLIGHT APP …` is a normal payment that needs a category, and (like Amazon/Venmo/PayPal) a note (`wrapperSourceOf` → `greenlight`; window bank date − message date in [−3, +7] days; payments already settled by a rule, such as the $6.62 plan fee or "$100 → Family Support", do not wait for one). (2) The only Greenlight message that matters is `$N allowance transferred to <child>`: it is stored as a `greenlight` note (the child's name) and the note matcher attaches it to the payment of the same amount. When a note is attached to a payment still needing a category, rules are re-run, so a rule on the note can apply. (3) A rule per child (`descriptor contains greenlight app AND note contains <name>` → the child's former category, suggest mode) is created from the old profiles. (4) Everything the cards do (spending, withdrawals, returns, declines, requests, reminders) is ignored: no transactions, no pushes, no wallet, no forecast, no Greenlight page, no "Greenlight settled" month item. (5) `retireGreenlight` runs once at start: removes the funding-as-transfer rule and restores the rows it hid, ignores (keeps, restorable) transactions the old engine made on the wallet, re-reads stored messages, closes open requests. The legacy kinds (`greenlight_allowance|return|reclass`) and tables stay in the schema so old data and audit stay intact. Limitation: matching assumes a funding payment and an allowance message have the same amount; when they do not (one $150 funding, two transfers), type the note or use a rule on the amount.

## D80. A payment is counted once: history overlap, identical alerts, and what stays visible
A mortgage payment showed twice because the bank file overlapped the history imported from the old sheet (kept on its own "Legacy" account, so the importer's duplicate check never saw it). Now: (1) `matchHistory` treats a bank row as already present when a history row has exactly the same amount, a date within 3 days, and a matching description (same cleaned name or ≥ 50% shared words); an equal amount alone is never enough, because silently dropping a real payment is worse than a duplicate you can see. Matching is one-to-one and deterministic, and `history_claims` records which history row a bank row was, so re-imports and the clean-up agree. (2) `dedupeAgainstHistory` hides (as "duplicate of earlier history", kept with its fingerprint so a re-import cannot bring it back, restorable) rows an earlier import had already put on top of history, moving any answer, note or flag you had given the bank row onto the history row first. It runs once at server start and after every import over the dates imported. (3) Two identical pending alerts (two identical coffees) are interchangeable, so the alert-to-posted matcher no longer treats a tie between them as ambiguous; before, both stayed pending next to their posted rows. (4) What cannot be decided automatically is shown: Months "No duplicates" and Transactions "needs=dupes" now also list a bank row with a same-amount history row it was not recognised as, and the same bank line under two accounts of one bank. (5) `test/no-double-count.test.ts` delivers the same real payments in random order and repetition (alerts, files, overlapping files, late alerts, twins; Chase and Wells Fargo; history overlap) and requires each to be counted exactly once.

## D81. The cushion sits above the current monthly budget
It was an absolute floor (an envelope kept at least the cushion). It is now the amount kept above the budget in force that month: floor = monthly budget + cushion, so a $150 budget with a $50 cushion is only drawn on when it holds more than $200, and then only the excess (`keepFloor` in `core/transfers.ts`; the budget used is the one effective in the month of the rebalance date). Not set is unchanged: a discretionary envelope can give everything, a non-discretionary one is immune. An explicit cushion of 0 now protects the month's budget. Cushions entered under the old meaning keep their number but now protect more (their budget is added), so review them on Categories, which shows "keeps $X" (budget + cushion) beside each.

## D82. An empty cushion is a cushion of 0; non-discretionary envelopes are asked second, not never
Supersedes the "not set" rules in D81. Every envelope keeps its current monthly budget plus its cushion (empty counts as 0) and can give only what is above that. Order is unchanged (§13.1): the income pool first, then discretionary envelopes, then non-discretionary ones, and only if the earlier groups could not cover the overage. The old "non-discretionary with no cushion is immune" is gone: to protect an envelope from ever being drawn on, give it a cushion large enough to cover what you would accept leaving in it.

## D83. Rebalance proposals also top up overspent envelopes with the budget for the days left in the month
`proposeRebalance` runs two rounds, each in priority order and each pool-first, then discretionary donors, then non-discretionary donors (above budget + cushion). Round 1 covers every overage. Round 2 asks each overspent envelope to also receive `monthly budget × days remaining ÷ days in month` (Bricks at -$70, $150 budget, day 11 of 30: $70 + $150 × 19/30 = $165 in total), so it can get through the rest of the month at its budgeted pace; on the last day the top-up is 0, using only what round 1 left, so a top-up can never take money an overage needed. Round 2 is best-effort: unfunded top-up is reported in `topUps` and is not a shortfall. It can be switched off (`?topUp=0`, checkbox on Transfers). Only overspent envelopes are topped up, donors still keep their own budget + cushion, and an overspent envelope never donates. The proposal's lines are merged per from/to pair and remain editable before commit.

## D84. Non-discretionary envelopes never give (supersedes D82's second tier)
Covering an overage (the overage itself and the top-up for the days left, D83) draws only on the income pool and then on discretionary envelopes above their monthly budget + cushion (empty = 0). A non-discretionary envelope (mortgage, insurance…) is never drawn on, whatever it holds and whatever its cushion, so the cushion field is disabled for them on Categories ("never gives"). To let an envelope give, mark it discretionary.

## D85. Overspent envelopes are funded in full, one at a time, in priority order (supersedes D83's two rounds)
Each overspent envelope is funded for its overage plus the budget for the days that remain (`monthly × remaining ÷ days`, unless the top-up is switched off) before the next envelope in priority order receives anything. Money for each envelope comes pool first, then from discretionary envelopes above their budget + cushion. A higher-priority envelope's top-up is therefore funded before a lower-priority envelope's overage; the way to steer the result is to change the overage priorities and press Propose again. Example: $500 available, Bricks (priority 1) at -$300 with a $150 budget and Sand (priority 2) at -$100 with a $100 budget: Bricks receives its overage and its days-remaining share first, and Sand gets whatever is left. An envelope's unfunded top-up is reported with the top-up; only an unfunded overage appears under "Unfunded".

## D86. Analytics chart heights, Explore table controls, and a dismissable "went over budget" heads-up
(1) Analytics reuses one chart element across tabs, and tabs that need a special height set it directly, so a tall chart's height carried over to the next tab (Category trend after Budget vs actual). Every tab now starts from the 380px default. (2) Explore's Spend by tables have a search box, sortable columns (name, transactions, spent; months open newest first), a footer total for what matches, and the usual pager (25/50/100/200); all client-side since the full list is already loaded. (3) When an AUTOMATIC categorization (a rule in auto mode) takes an envelope's balance from zero-or-more to below zero, a `notices` row is raised and shown at the top of Home with "No action needed" and a Dismiss button. Only the crossing payment raises it, only for recent spending (within 35 days of the newest data, so bulk history imports are silent), and at most one open notice per category; after dismissal the next crossing raises a new one. "Over budget" here means the envelope balance (what the rebalance also calls an overage), not spending above the monthly amount.

## D87. Weekly budgets

A weekly budget spreads **one category's monthly budget** over the weeks of the month and counts net spending (refunds count back) in that category. It is a view over existing spending: it moves no money, creates no envelope and changes no category balance.

- **One category, no typing.** It is named "<category> Weekly" and its total is that category's budget for the month shown, so it follows the category's budget when that changes (earlier months keep what the budget was then). To change the amount, change the category's budget. A category can have one weekly budget; the category must be an active expense category with a monthly budget above zero. Chosen with the same category picker used everywhere.
- **Weeks** start on a chosen weekday (default Monday) and are cut at month ends, so a month can begin and end with a short week. Each week's share is by days, rounded cumulatively, so the weeks add up to the month exactly. The running total by the end of each week is shown as the week's limit.
- **What is left carries, and it starts from the envelope.** A week's money is its share plus whatever was left (or overspent) the week before, so a week that goes over eats into the next and unspent money rolls forward. The first week also gets what the category's envelope held when the month began (earlier months' leftovers), and this month's transfers (coverages, rebalances) are applied to that opening amount, because they correct the envelope's level rather than being spending: counted in the week they happened, an overspent envelope would show a deficit in the weeks before its coverage arrived. So the weekly total *is* the envelope's balance, the same number the Budget page and Home show for that category, and the last week's remainder equals it.
- **Favorites** are per person (`weekly_favorites`) and show on Home as tiles *above* the favorited envelopes. On Home it is a card like the other favorites but spans every column of the grid. Home's fallback list of a few envelopes appears only when nothing at all is pinned.
- Deleting a weekly budget removes it and its pins and touches no transactions.
